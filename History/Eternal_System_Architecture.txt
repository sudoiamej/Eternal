1. APPLICATION OVERVIEW & TARGET AUDIENCE DESIGN
================================================================================
Eternal is a state-of-the-art Windows system intelligence, forensic analysis, 
and maintenance suite built using WPF (.NET 10.0). The system is engineered to 
interact directly with bare-metal Windows architectures, system configuration 
stores, the Registry, active process memory structures, and hardware sensors.

The application serves three distinct user categories (Audience Segments):

1.1. NON-TECHNICAL USERS ("System Physician")
- Simplified Conceptual Model: Abstracted metrics (e.g. 0-100 "Trust Score") 
  that turn complex security variables into immediate cognitive feedback.
- Guided Actions: Danger zones are locked out or wrapped in confirmation screens 
  to prevent accidental registry or boot record corruption.
- Visual Peace of Mind: Hearts, glowing visual auroras, and clear status 
  gauges remove standard CLI anxiety.

1.2. INTERMEDIATE USERS ("Power Dashboard")
- Expanded Telemetry: Direct access to thermal readings, raw voltage metrics, 
  and hardware performance states.
- Performance Optimizations: Multi-process grouping, memory heap compaction, 
  and SCM Delayed-Startup management.

1.3. FORENSICS & ADMINISTRATIVE EXPERTS ("Forensic Toolset")
- Shannon Entropy calculations to expose binary encryption/obfuscation.
- Import signature tracking for Windows Injection APIs (e.g. VirtualAlloc).
- Boot BCD record modifications via low-level Windows registry & bcdedit hooks.
- Direct process digital signature verification bypassing slow shell loops.

2. ARCHITECTURAL & MVVM PATTERN IMPLEMENTATION
================================================================================
The application is structured strictly according to the Model-View-ViewModel (MVVM) 
design pattern to enforce a clean separation of concerns:

                         +---------------------+
                         |      App.xaml       |
                         | (Composition Root)  |
                         +---------------------+
                                    |
            Instantiates and Registers Services / ViewModels
                                    |
                                    v
                         +---------------------+
                         |  Dependency Inject  |
                         |  (ServiceProvider)  |
                         +---------------------+
                                    |
         +--------------------------+--------------------------+
         |                                                     |
         v                                                     v
+------------------+     Binds DataContext via XAML     +------------------+
|      Views       |----------------------------------->|    ViewModels    |
| (UI Layer, XAML) |<-----------------------------------|  (State & Cmds)  |
+------------------+         Updates Properties         +------------------+
         ^                                                     |
         |                                                     | Invokes
         |                                                     v
         |               Fires Updates/Callbacks        +------------------+
         +----------------------------------------------|     Services     |
                                                        |  (System APIs)   |
                                                        +------------------+

2.1. COMPOSITION ROOT (App.xaml.cs)
All viewmodels and system services are registered inside App.xaml.cs using a 
central Dependency Injection (DI) system. Services are registered with their 
interfaces (e.g. `IBootService` mapped to `WindowsBootService`) to promote 
loose coupling and simplify testing.

2.2. DATA BINDING AND NOTIFICATIONS
ViewModels inherit from a base BindableBase or ViewModelBase class implementing 
`INotifyPropertyChanged`. Custom commands implement `ICommand` (such as RelayCommand) 
to route visual interactions directly from XAML to code-behind logic without 
tight coupling.

2.3. EXPLICIT SYSTEM NAMESPACE DECLARATIONS
Due to overlapping project namespaces (e.g., Eternal.Services.System), all standard 
C# system-level calls (like System.Diagnostics.Process or System.IO.File) are 
prefixed with global qualifiers (e.g. `global::System.IO` or `global::System.Diagnostics`) 
to prevent MSBuild clashing (MC3024 / CS0234 compiler warnings).

3. SYSTEM SUBSYSTEMS DEEP DIVE
================================================================================

3.1. BOOT ARCHITECTURE EDITOR
- Service: `WindowsBootService` (implementing `IBootService`)
- ViewModel: `BootViewModel`
- Mechanics: Direct parsing of the Windows BCD (Boot Configuration Data) store 
  using administrative WMI wrappers (`root\WMI\BcdStore`) or `bcdedit.exe` execution.
- Features: Adjusts system boot timeouts, toggles Safe Boot states for registered 
  loaders, and allows safe loader deletions.
- Critical Constraints: Programmatically checks for `{current}` and `{bootmgr}` 
  GUID keys, strictly disabling delete actions for these records to ensure 
  the operating system remains bootable.

3.2. SENTINEL PRIVACY AUDITER
- Service: `WindowsPrivacyService` (implementing `IPrivacyService`)
- ViewModel: `PrivacyViewModel`
- Mechanics: Directly queries Windows telemetry registry keys, ETW (Event Tracing 
  for Windows) channels, and diagnostic logging folders.
- Telemetry Sweeper: Scans directory `C:\ProgramData\Microsoft\Diagnosis\ETMLogs` 
  and safely purges active diagnostic trace files (`.etl`). 
- Interactive Gauge: Uses a custom radial gauge displaying continuous percentage 
  updates during file scrubbing to satisfy Norman's "System Status Visibility."

3.3. FORENSIC ENTROPY ANALYZER
- Service: `WindowsFileForensicsService` (implementing `IFileForensicsService`)
- ViewModel: `FileForensicsViewModel`
- Shannon Entropy: Computes the logarithmic distribution of byte values in a stream 
  (from 0.0 to 8.0). Values exceeding 7.2 represent highly ordered bytes, signaling 
  custom encryption, packing, or obfuscation common in malware.
- API Scan: Direct in-memory parsing of portable executable structures (PE imports) 
  scanning for known loader injection routines: `VirtualAlloc`, `VirtualAllocEx`, 
  `WriteProcessMemory`, `CreateRemoteThread`, and `QueueUserAPC`.

3.4. PRECISION STRESS BENCHMARK
- Service: `WindowsThermalService` (implementing `IThermalService`)
- ViewModel: `HardwareStressViewModel`
- Engine: Uses multi-threaded worker pools executing complex cryptographic 
  computations. Supports flat load profiles and cyclical Cosine duty-cycle patterns.
- Thermal Safety Shield: Runs an asynchronous daemon polling hardware sensors 
  every 500ms. If CPU package temperature hits or exceeds 88 degrees C, the daemon 
  forces an emergency interrupt of all stress worker threads and returns a visual 
  Thermal Throttling Halt status.

3.5. DRIVER PACKAGE ARCHIVER
- Service: `WindowsDriversService` (implementing `IDriversService`)
- ViewModel: `DriversViewModel`
- Packaging Loop: Queries the Windows SCM for active device drivers. Filters out 
  standard hardware architectures and copies target active `.sys` files.
- Export Packaging: Compiles a diagnostic `driver_manifest.txt` describing 
  driver versions, hashes, and loaded memory offsets, zipping them directly 
  into a compressed ZIP archive in the base app directory.

3.6. SERVICES OPTIMIZER
- Service: `WindowsServicesService` (implementing `IServicesService`)
- ViewModel: `ServicesViewModel`
- Mechanics: Interfaces directly with the Windows Service Control Manager (SCM).
- SCM Boot Delay: Configures service boot properties via standard Win32 APIs 
  or registry hooks by modifying `DelayedAutostart = 1` inside:
  `HKLM\SYSTEM\CurrentControlSet\Services\<ServiceName>`. This delays non-essential 
  startup processes to accelerate OS boot cycles.

6. HCI INTEGRATION STANDARDS (DON NORMAN FRAMEWORK)
================================================================================
Eternal is meticulously built around the principles defined in Don Norman's 
seminal work, "The Design of Everyday Things." Every feature incorporates these five 
human-computer interaction paradigms:

6.1. THE CONCEPTUAL MODEL (Mental Models)
- App Interface: Instantly matches the user's expectations. Green means healthy, 
  blue means processing, red/orange means warnings that require attention.
- Hacker gate vs Admin dashboard: Offers a clear conceptual boundary for different 
  user groups (Developer Monospaced terminal vs Clean consumer gauges).

6.2. VISIBILITY OF SYSTEM STATUS
- Radial Sweeper Gauge: A visual vertical scanline sweep and dual Concentric 
  rotating dashed rings convey that background processes are successfully auditing, 
  removing "frozen window" concerns.
- Monotonic Progress Indicator: Ensures progress never steps backward during scans 
  or jumps ahead unexpectedly, accurately reflecting system status.

6.3. MAPPING & AFFORDANCES
- Dynamic Keypad Dot Gate: Affords input of a 6-digit security code. Clicking dots 
  fills visual icons, confirming input mapping naturally.
- Sidebar Collapse Chevron: Signifies expanding/collapsing. Hovering over sidebar 
  options invokes "card lifts" to signify clickability.

6.4. INTERACTIVE FEEDBACK
- Lockout Attempt Shake: The 3-dot attempt track physically translates/shakes on 
  password failure, providing sensory rejection feedback.
- Toast Compaction Compactor: Compacting heap memory immediately triggers a sliding 
  holographic notification box confirming saved megabytes.

6.5. LOGICAL & PHYSICAL CONSTRAINTS
- Boot Protected Records: System prevents deleting `{current}` and `{bootmgr}` loader 
  records, mapping absolute safety boundaries.
- Thermal Benchmark Halt: Stress benchmarking checks temperature limits continuously, 
  disabling threads before a physical overheat occurs, enforcing hard constraints.
